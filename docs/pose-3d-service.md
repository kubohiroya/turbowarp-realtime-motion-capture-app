# 3Dサービス（#34、M-10）

最大6人を追跡する3Dサービスです。interface v1、実装`fusion-v0`（時刻整列・対応付け・三角測量）、stub、
評価の土台、アプリ側の転送・検証・状況表示・timeout処理を実装しています。所有境界は#11、設計は#34を
正とします。

## 置き場所

`packages/pose-3d-service`（ワークスペース内のパッケージ）。別パッケージとして再利用する予定や互換の別実装を
提供する予定が当面ないため、まずアプリ内で作り、必要になった時点で切り出します。fusion appのSB3には
TurboWarp拡張`realtimemotioncapturepose3dservice`として埋め込まれ、サービスはその拡張が起動する専用Web Worker
（ビルド時にインライン化）で動きます。

| ファイル                           | 内容                                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `src/contracts.ts`                 | interface v1（`twrmc/pose-3d-service` v1）、`twrmc/pose-frame-3d` v2、上限、エラーコード、検証、v1への変換    |
| `src/service.ts`                   | サービス側。`fusion-v0`とstub実装`stub-normal`／`stub-timeout`／`stub-invalid`                                |
| `src/fusion/`                      | `fusion-v0`の中身。`jitter-buffer.ts`（L0）、`fuse.ts`と`geometry.ts`（L1）、`estimator.ts`（契約への出入り） |
| `src/worker.ts`                    | Workerの入口                                                                                                  |
| `src/client.ts`                    | fusion app側。送る前の検証、重複・古いフレームの除外、timeout、応答の検証、状態                               |
| `src/extension.ts`、`src/entry.ts` | TurboWarp拡張とWorkerの起動                                                                                   |

## interface v1

すべてのメッセージが`interface: twrmc/pose-3d-service`、`version: 1`、`id`、`type`、`payload`を持ちます。

| 方向          | type                                        | payload                                                                                                                                 |
| ------------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| app → service | `configure`                                 | `implementation`、`referenceId`、`cameras[]`（`cameraId`＝ペアリングのpeer名、歪みを含むcamera model、`cameraFromReference`、時刻対応） |
| app → service | `frame2d`                                   | `cameraId`と、受信した`twrmc/pose-frame-2d`（変更しない）                                                                               |
| app → service | `requestPose3d`                             | `timestampUs`（v1では`null`＝最新）                                                                                                     |
| service → app | `configured`／`accepted`／`pose3d`／`error` | 設定したカメラ、受理したsequence、`twrmc/pose-frame-3d` v2または`null`、エラーコードと理由                                              |

固定値：人数6、カメラ2〜8台、1メッセージ65,536バイト、configure timeout 2,000 ms、3D request timeout 100 ms、
転送するフレームの経過時間500 ms。

`twrmc/pose-frame-3d` v2は、v1に`referenceId`、`implementation`、人物ごとの`identitySource`、関節ごとの
`sigma`、`state`（`measured`／`constrained`／`predicted`／`missing`）、`cameraIds`を加えたものです。
`measured`は2台以上のカメラを必要とし、`missing`は位置を持ちません。`latest 3D pose JSON for avatars`は
アバター用blockが読むv1へ変換し、`measured`と`constrained`以外の関節をscore 0にします。

## fusion app

フラグ`external3dServiceV1`（`packages/app-shell/src/apps/fusion.ts`の`appFlags`）が有効なときだけ、
メニューに「3D統合を開始する」「3D統合を止める」が出ます。アプリが要求する実装は`fusion-v0`です。
実機で測るまでは既定で無効のままにしています。

開始すると、次を行います。

1. 空間と時刻の校正がREADYでなければ始めない。
2. 校正で返ってきた各カメラのcamera model、配置結果、時刻対応から設定を組み立て、Workerを起動して適用する。
3. 毎フレーム、姿勢を送ってきた各カメラの最新フレームを経過時間とともに渡し、3D poseを要求する。
   - 同じsequence、500 msより古いフレーム、不正なフレーム、配置時と別のcalibrationのフレームは送らない。
   - `captureTimestampUs`は変えない。
4. 1秒ごとに、実装名、人数、RTT、3Dの経過時間、送信・古い・不正・拒否の件数、各カメラの2Dの経過時間を表示する。
   timeoutや不正な応答のときは3D出力を空にし（`degraded`）、理由と2Dの状況を表示し続ける。
   有効な応答が戻れば`ready`に戻る。

## アバターへの出力

fusion appは、3D統合の出力から演者ごとのVRMアバターを表示します（`scripts/app-scripts/avatar.ts`）。
アバターを動かす`turbowarp-realtime-motion-capture`のblockは、3Dの`personId`と同じ`trackingId`を持つ
2Dの人物を対にして読みますが、3Dの`personId`と同じIDの2Dを出すものはありません。そこでサービスが
アバター用の出力を作ります（`src/avatar-poses.ts`）。

| block                                                                | 内容                                                                       |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `update avatar poses for [SLOTS] slots releasing after [HOLD_MS] ms` | 最新の3Dを`slot-1`〜`slot-N`の枠へ割り当て、各人物の2Dと対にする           |
| `avatar 3D pose JSON`／`avatar 2D pose JSON`                         | `personId`と`trackingId`を枠のIDに置き換えたPoseFrame3D v1とPoseFrame2D v1 |
| `avatar slots JSON`                                                  | どの人物がどの枠にいるか                                                   |

- **枠**：現れた人物は空いている最も小さい番号の枠を取り、見えている間は保ち、`HOLD_MS`見えなければ
  空けます。アバターは起動時に一度だけ枠へbindするため、人物が入れ替わるたびにVRMを読み直しません。
  アバターが別の人へ移るのは、fusion-v0がその人に新しいIDを付けたとき（下の「時間方向の人物同定」）です。
- **2D**：3Dの人物が統合された元の2Dの人物（人物の`views`：カメラと追跡ID）を、そのカメラの最新の
  2Dフレームから取ります。サービスが
  統合した時刻より少し新しいフレームですが、Kalidokitが読む画面上の位置には十分です。大きさの違う
  カメラの人物は、最初のカメラの大きさへ拡大縮小して1つのフレームにします。
- **測れなかった関節**：v1では原点・score 0になります。Kalidokitは全関節をまとめて解くため、原点の関節が
  長さ0の手足を作ると回転が有限でなくなり、その人物がまるごと失われます。そこで枠ごとに各関節を最後に
  測れた位置に保ち（score 0のまま）、一度も測れていない手足と顔の関節は、腕と脚を胴体に沿って下ろし頭を
  肩の上に置いた位置に置きます。score 0の関節を使う骨は、アバターのblockが回転を変えません。両肩と
  両腰がそろって測れたことのない人物は出力しません。

合成データ（カメラ2台・2人・3秒、seed 1）で、TurboWarp-A-Frame 0.5.0とrealtime-motion-capture 0.5.0の
ビルドへ流し、90フレームすべてでエラーなく、2体が表示され、56フレームで2体とも、34フレームで1体が
動きました。関節の置き換え前は、手首と足首が測れない人物が毎フレーム失われていました。

**制約**：アバターの立ち位置は、Kalidokitが画面上の腰から推定したものに`rootOffset`を足したもので、
3D統合が測った会場内の位置ではありません。同じカメラの画面上で近い2人は重なって見えます。

## fusion-v0（#34 段階3）

`kubohiroya/turbowarp-realtime-motion-capture`の`src/fusion`から、次の2層を移しました。移す前は
fusion appのページ内で動いていたもので、いまはサービスのWorkerで動きます。

| 層                    | 内容                                                                                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L0 時刻整列           | カメラごとに時刻順のリングバッファへ入れ、最新フレームの少し後ろの1つの時刻で全カメラを再標本化する。カメラは別々の瞬間に撮るので、違う瞬間のフレームを三角測量すると動いている手足が曲がる |
| L1 対応付けと三角測量 | その時刻の各カメラの人物を、2視点の再投影誤差で対応付け、COCO-17の各関節を検出の信頼度で重み付けして三角測量する                                                                            |

出力する時刻は「最新フレーム − 33 ms」（30fpsの1フレーム分）です。待てば揃いますが、その分だけ遅れます。
実機の記録で決め直します。

### 時間方向の人物同定（段階4）

各時刻の人物を、胴体の中心（両肩・両腰の平均）で前の時刻の人物へつなぎ、`person-1`、`person-2`…と
同じIDを保ちます（`src/fusion/identity.ts`）。

- 前の時刻の人物の中心から「余裕1.2 m＋秒速3 m×経過時間」の内側にいれば、近い組から同じIDにします。
- あるカメラの追跡IDが前と同じ人物（統合の元になった2Dの人物、`views`）は同じ人物の強い証拠として先に
  つなぎ、距離も4倍まで許します。混雑した時刻は三角測量を誤って中心が大きく跳ぶことがありますが、
  カメラの追跡IDはそれに引きずられません。
- どこにもつながらない人物には新しいIDを付け、1秒見えなかったIDは退けます。
- 余裕の値は合成データで決めました。広げるほど8台・6人の切り替わりが減り、1.2 mで下げ止まりました。
  会場の記録で決め直します。すれ違う2人を区別できないカメラしかなければ、IDが入れ替わることがあります。

10秒、ノイズ1.5px、seed 1／2／3の同定の切り替わり（関節の誤差と再現率は変わりません）：

| シーン         | 段階3（追跡IDから作るID） | 段階4      |
| -------------- | ------------------------- | ---------- |
| カメラ2台・1人 | 0／1／0                   | 0／0／1    |
| カメラ4台・3人 | 7／10／3                  | 1／0／0    |
| カメラ8台・6人 | 53／47／45                | 28／27／24 |

3Dの人物は、統合の元になった2Dの人物を`views`（`{cameraId, trackingId}`の配列）として持ちます。

### 予測（段階6の外挿）

統合する時刻は「最新フレーム − 33 ms」で、画面に出るのはさらに後です。`predict 3D pose to [LEAD_MS] ms after
each request`を設定すると、クライアントは要求のたびに「最新フレームの撮影時刻＋その受信からの経過＋LEAD_MS」
を撮影時計での目標時刻としてサービスへ渡し（`requestPose3d`の`predictToUs`）、サービスは各関節を目標時刻まで
外挿して`state`を`predicted`にします（`src/fusion/prediction.ts`）。

- 同じ人物IDの直近400 msの位置に最小二乗で直線を当て、その速度で進めます。点が3つ未満の関節、直線からの
  二乗平均が3 cmを超える関節（三角測量の誤りやIDの取り違え）は外挿せず、統合した位置のままにします。
- 速度は秒速3 m、外挿は200 msまでに抑えます。フレームの`timestampUs`は目標時刻になります。
- v1への変換（`latest 3D pose JSON for avatars`）は`predicted`をscore 0にするため、fusion appはアバター用の
  出力でだけ予測を使います（LEAD_MSは0。画面までの遅延は未測定）。

評価ツールに`--lead-ms`（要求から表示までの時間）と`--predict`を加え、表示する時刻の真値（前後のフレームから
補間）との誤差を`display error`として出します。10秒、seed 1の中央値／95パーセンタイル（m）：

| シーン         | 表示までの時間 | 予測なし       | 予測あり       |
| -------------- | -------------- | -------------- | -------------- |
| カメラ2台・1人 | 0 ms           | 0.0368／0.1131 | 0.0242／0.1134 |
| カメラ2台・1人 | 50 ms          | 0.0598／0.2002 | 0.0309／0.2017 |
| カメラ4台・3人 | 0 ms           | 0.0361／0.1123 | 0.0271／0.1124 |
| カメラ4台・3人 | 50 ms          | 0.0592／0.1980 | 0.0413／0.1984 |
| カメラ8台・6人 | 50 ms          | 0.0609／0.2116 | 0.0566／0.2136 |

2点から速度を求めると予測なしより悪くなり（4台・3人、50 msで0.0753）、当てはめる窓を広げて改善しました。
残差の上限は、95パーセンタイルを予測なしより悪くしないために入れています。8台・6人では残差の条件で外挿を
控える関節が多く、改善は小さいままです。値は会場の記録で決め直します。

**まだ無いもの**（関節ごとの`state`で区別しています）

- 骨格の制約（段階5）、欠損の補完と平滑化（段階6）。そのため`constrained`は出ず、`predicted`は予測を
  求めたときだけ出ます。

## 評価の土台（#34 段階2）

3D推定の中身を作る前に、良し悪しを測る道具を用意します。段階3以降は、ここで決めた形式と指標で比べます。

| ファイル                  | 内容                                                                                                                                                                                                                                                     |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/session.ts`          | セッション（`twrmc/pose-3d-session` v2はJSONL、v1の単一JSONも読む）。サービスに渡したものを渡した順に、時刻付きで持つ。合成データのときは正解も持つ。`SessionRecorder`は、実行中のアプリから記録するための入れ物（件数で上限を切り、古いものから捨てる） |
| `src/synthetic.ts`        | 合成シーン。seedから決まるので、同じ入力で何度でも測り直せる                                                                                                                                                                                             |
| `src/replay.ts`           | セッションを任意の実装へ流し込み、1メッセージごとの処理時間を測る。壁時計は待たないので、10秒のセッションはミリ秒で再生する                                                                                                                              |
| `src/metrics.ts`          | 正解との比較。件数を必ず添える                                                                                                                                                                                                                           |
| `scripts/pose-3d-eval.ts` | CLI                                                                                                                                                                                                                                                      |

### CLI

```
pnpm run pose3d:eval evaluate --cameras 4 --persons 3 --seconds 10
pnpm run pose3d:eval synthesize --out tmp/session.jsonl --seed 2
pnpm run pose3d:eval replay --session tmp/session.jsonl --implementation stub-timeout
pnpm run pose3d:eval evaluate --session ~/multiview-pose-recordings/take-1.jsonl.gz
```

`--session`は、JSONL（v2）でも単一JSON（v1）でも読み、名前が`.gz`で終われば展開します。会場の録画を
そのまま渡せます。`--out`も同じで、`.gz`で終わる名前なら圧縮して書きます。

`--session`を渡さなければ、その場で合成シーンを作って評価します。`evaluate`に`--json`を付けると、
そのままIssueに貼れるJSONを出します。

### 合成シーンが模すもの・模さないもの

模すもの：複数人が歩く、カメラごとの視点、キーポイントの雑音、画角外への移動、カメラごとに人を見失う区間
（オクルージョン）、カメラごとの追跡IDとその切り替わり。

模さないもの：レンズの歪み、ローリングシャッター、カメラ間の時計のずれ。これらは実機の記録で扱います。
合成データの良い数値を、そのまま会場での数値と読まないための区別です。

### 指標

| 指標             | 意味                                                               |
| ---------------- | ------------------------------------------------------------------ |
| 処理時間         | 1メッセージあたりのサービス内の時間（p50／p95／最大）              |
| 人数の誤差       | 報告した人数と、2台以上のカメラが見ていた人数の差                  |
| 関節の誤差       | 対応付けた関節の3D距離（m）。`measured`と`constrained`だけを数える |
| 関節の再現率     | 2台以上が見ていた関節のうち、位置を報告できた割合                  |
| 同定の切り替わり | 同じ人物の報告IDが変わった回数                                     |

正解の無いセッション（会場の記録）では、正解を要らない指標だけを出します。

### 段階1（stub）の基準値

10秒、seed 1、ノイズ1.5px。段階3以降は、同じ条件で比べます。

| シーン         | 処理時間 p50／p95 | 人数の誤差 平均 | 関節の誤差 p50／p95 | 再現率 | 同定の切り替わり |
| -------------- | ----------------- | --------------- | ------------------- | ------ | ---------------- |
| カメラ4台・3人 | 0.011／0.020 ms   | 0               | 3.72／5.74 m        | 1.00   | 13               |
| カメラ8台・6人 | 0.018／0.029 ms   | 0.39            | 4.28／9.21 m        | 0.93   | 21               |

stubは固定の姿勢を並べるだけなので、関節の誤差が数メートルになるのは当然です。この表は、段階3以降の
数値が「stubより良い」ことを言えるようにするためのものです。

### まだ無いもの

- 実行中のアプリからの記録（`SessionRecorder`を組み込み、セッションをファイルに保存する経路）。実機の記録を
  取る段階で入れます。
- 記録を再生しながらの可視化。

## local-app

local-app（#36 段階5）も同じ拡張と設定の部品を使い、同じフラグで有効にします。1ページで全カメラを推定するため、
2Dフレームの`peerId`はすべて`local`で、カメラは設定したカメラID（`cam-1`…）で区別します。stubの`cameraIds`も
設定したカメラIDです。詳しくは[local-app](local-app.md)。

## 検証の状況

- 自動：`pnpm check`。パッケージの契約テスト26件（検証、stubの3実装、client の重複・古いフレーム・
  calibration不一致・timeout・不正応答・Worker失敗、拡張のblock）。
- ブラウザ：フラグを一時的に有効にしたfusion appのプレイヤーをローカルホストで配信し、2台分の合成2Dフレーム、
  配置結果、READYを与えて、メニューから開始した。
  - パッケージ化したプレイヤー内で実際のWorkerが起動し、stub-normalの`PoseFrame3D` v2（2人、17関節、
