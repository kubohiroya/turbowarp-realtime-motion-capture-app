# 実機での毎秒フレーム数と遅延の計測

実物のカメラとMoveNetを動かしたまま、毎秒何フレーム出て、撮影からポーズになるまで何ミリ秒かかるかを測る
手順です。机上の計測（[ポーズの録画と再生](pose-replay.md)の「長時間の録画（実測）」）は記録経路だけを
測っていて、推論の負荷と実カメラの揺らぎは入っていません。ここではそれを会場のPCで測ります。

測った結果は #36（実機計測）に、下の「記録用テンプレート」を埋めて貼ってください。

## 何を、どこで測るか

| 指標                                                               | どこで測るか                                         |
| ------------------------------------------------------------------ | ---------------------------------------------------- |
| カメラが実際に出したfps、間隔のばらつき、抜け                      | 録画を`pnpm run analyze:recording`にかける           |
| 撮影→ポーズの遅延（MoveNet推論、フレーム待ち、VMの順番待ちの合計） | 同上（録画の`atUs − captureTimestampUs`）            |
| カメラ間の撮影時刻のずれ（local-appで複数台）                      | 同上                                                 |
| 推論1回の時間、推論fps、撮影→結果                                  | 姿勢推定中の表示（local-app／camera app）            |
| 統合アプリでの2Dの古さ、3Dの経過                                   | 統合アプリの「3D統合」の表示（camera appで測るとき） |
| 録画が推論の邪魔をしていないか                                     | 同じ条件で、録画あり／なしを1回ずつ                  |

録画には、1フレームごとに同じページの時計で2つの時刻が入っています。カメラがそのフレームを撮った時刻
（`captureTimestampUs`、カメラのフレームコールバックから）と、そのフレームがポーズとしてアプリに届いた時刻
（`atUs`）です。前者の間隔がフレームレートを、2つの差が撮影からポーズまでの遅延を表します。

## 準備

1. **計測用ビルドを作る。** 録画（DEBUG_POSE_REPLAY）と3Dサービス連携を有効にしたビルドです。配布物と
   違うのはこの2つのフラグだけです。

   ```bash
   pnpm run build:measurement
   ```

   フラグを選ぶときは`TWRMC_APP_FLAGS`で渡します（例：`TWRMC_APP_FLAGS=debugPoseReplayV1`）。存在しない
   フラグ名はビルドを止めます。

2. **いつものポートで起動する。** 保存済みのレンズ校正はポート（origin）ごとなので、配布物と同じポートで
   動かします。

   ```bash
   pnpm run serve:app -- local-app
   ```

   camera appとfusion appも同じように`serve:app -- camera-app`、`serve:app -- fusion-app`です。

3. **録画の置き場所**は`~/multiview-pose-recordings`です（`TWRMC_RECORDINGS`で変えられます）。

4. **終わったら元に戻す。** 計測用ビルドはコミットしません。

   ```bash
   pnpm run build
   ```

## 手順A：local-app（1台のPCに複数のUSBカメラ）

いちばん手軽で、カメラ間のずれも同じ時計で測れます。

1. 「カメラを探す」で全台を開き、「解像度を切り替える」で測りたい解像度にする。解像度と、カメラ一覧の
   表示（実際に出ているfps）を控える。
2. レンズ校正を済ませる（普段どおり）。
3. 「姿勢推定を始める」。表示の`1周○ms 撮影時刻のばらつき○ms — camera-1: 推論○ms ○fps 撮影→結果○ms`を
   30秒ほど見て、典型的な値を控える。`（撮影時刻なし・表示時刻で代用）`が出ていたら、そのカメラは撮影時刻を
   持っていないので、遅延は実際より短く出る。これも控える。
4. 「ポーズの録画を始める」で、長さ`300`、fps`0`（制限なし）を入れる。5分たつと止まる。
5. 「ポーズの録画を止めて保存する」で番号を付ける（例：`1`）。`local-app-1.jsonl.gz`になる。
6. 解析する。

   ```bash
   pnpm run analyze:recording -- ~/multiview-pose-recordings/local-app-1.jsonl.gz --fps 30
   ```

   `--fps`にはカメラに要求したfpsを入れる。届いた割合が出る。

7. 同じ条件で、録画をせずに30秒ほど姿勢推定の表示を見る。手順3の値と比べて、録画が推論を遅くしていないかを
   確かめる。
8. 人数（1人、2人、…）とカメラ台数を変えて繰り返す。

## 手順B：camera app＋fusion app（WebRTC越し）

カメラごとに1台のPCで、統合アプリまでの経路を含めて測ります。

1. 統合アプリ（`serve:app -- fusion-app`）とカメラアプリ（各PCで`serve:app -- camera-app`）を起動し、
   QRペアリングで接続する（[QRペアリング](qr-pairing.md)）。
2. 各カメラアプリで「姿勢推定を始める」。表示の`FPS`・`推論1回（フレーム待ちを含む）`・`送信`・`破棄`・
   `送信量`を控える。
3. 統合アプリで空間と時刻を校正し、「3D統合を開始する」。表示の`3D経過`と、`2D: camera-1 ○ms前`を控える
   （統合アプリに届いた2Dの古さ）。
4. 各カメラアプリで「ポーズの録画を始める」（長さ`300`、fps`0`）、終わったら保存する。
5. 各カメラの録画を解析する。

   ```bash
   pnpm run analyze:recording -- ~/multiview-pose-recordings/camera-app-1.jsonl.gz --fps 30
   ```

camera appの録画は1台ぶんなので、カメラ間のずれは出ません。カメラ間の揃い方は、統合アプリの校正結果
（時刻対応）で見ます。

## 解析の出力の読み方

```
local-app-1.jsonl.gz (debug-pose-replay)
  camera-1: 8990 frames over 299.9 s
    frame rate     30 fps (99.9% of 30 fps asked)
    interval       median 33.3 ms, p95 34.1 ms, max 67.2 ms
    gaps           3 (longest 67 ms), sequence skips 0
    capture->pose  median 41.2 ms, p95 58.9 ms, max 120.4 ms
    persons        mean 1.98, max 2, none in 12 frames
  camera-1 vs camera-2: nearest frame median 4.1 ms, p95 15.8 ms apart
```

（数値は読み方の例です。）

| 行                | 意味                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------- |
| `frame rate`      | 撮影時刻の間隔から求めた、実際に届いたfps。`--fps`を渡すと要求に対する割合も出る              |
| `interval`        | フレーム間隔。p95やmaxが中央値から離れていれば、揺らぎや詰まりがある                          |
| `gaps`            | 中央値の1.5倍を超えた間隔の数。カメラか推定器が出さなかったフレーム                           |
| `sequence skips`  | フレーム番号の飛び。推定したのに記録されなかったフレーム（録画のfps制限を使ったときも増える） |
| `recorded twice`  | 同じフレームが2回記録された数。解析では1つに数える                                            |
| `capture->pose`   | 撮影からポーズがアプリに届くまで。MoveNetの推論、推論待ちのフレーム、VMの順番待ちの合計       |
| `clocks disagree` | ポーズが撮影より前に届いたことになっているフレーム。撮影時刻の出どころを疑う                  |
| `nearest frame`   | 1台目の各フレームに最も近い、他のカメラのフレームとの時刻差。3Dにするときの揃い方の目安       |

`--json`を付けると、同じ内容をJSONで出します。
