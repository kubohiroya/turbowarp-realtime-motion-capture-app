# ポーズの録画と再生（DEBUG_POSE_REPLAY）

カメラの先にある処理（対応付け、三角測量、同定、アバター）は、同じ動きに対して何度も試す必要があります。
しかし本番の動きは二度と同じになりません。そこで、推定した2Dポーズを、そのときの校正ごとファイルに記録し、
あとからカメラなしで再生できるようにしています。

録るのはカメラの映像ではなく、推定したあとの2Dポーズ（COCO-17）です。

フラグ`debugPoseReplayV1`（各アプリの`packages/app-shell/src/apps/*.ts`の`appFlags`）が有効なビルドでだけ、
メニューに出ます。既定では無効で、そのときはブロックも登録されません。

## 置き場所はファイル

ブラウザの保存領域はoriginごと（アプリごとにポートが違う）なので、camera appで録ったものをfusion appから
読めません。会場用ローカルホストが`/recordings`で同じディレクトリを読み書きするので、3つのアプリが同じ録画を
使えます。置き場所は`TWRMC_RECORDINGS`、既定はホームの`multiview-pose-recordings`です。詳しくは
[ローカルホスト](local-host.md)。

ローカルホストを使わない起動（TurboWarpでSB3を開くなど）では、ファイルの書き出しと読み込みで代用します。

## 録画の指定（長さとfps）

録画を始めるとき、長さ（秒）と、1秒あたりに記録するフレーム数（fps）を指定できます。どちらも0にすると、
その制限はかけません（0秒＝止めるまで、0fps＝推定できたフレームをすべて）。

| 指定       | 動作                                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------- |
| 長さ（秒） | その長さぶんの動きを記録したら、自動で止めます。始めてから放っておけます                                            |
| fps        | カメラごとに1秒あたりその数まで記録し、間は捨てます。長い録画を小さくしたいときや、遅いPCで再生したいときに使います |

どちらもフレーム自身の撮影時刻で判断します。ページが一瞬固まっても、録画の長さは映っている動きの長さのままです。
再生は録ったときの間隔で流すので、10fpsで録れば10fpsで再生されます。

要約の表示には、指定した値と、間引いた件数も出ます。

## 形式

`twrmc/pose-3d-session` v1です。3Dサービスの評価ツール（#34 段階2）がそのまま再生できるので、会場で録ったものを
机上で指標にかけられます。

| 項目            | 内容                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------- |
| `configuration` | 3Dサービスの設定（カメラのモデル・配置・時刻対応）。local-appの録画はこれを持ちます             |
| `spaceTime`     | カメラごとの空間と時刻の測定結果（`twrmc-sync-result`の中身）。camera appの録画はこれを持ちます |
| `events`        | `frame2d`（カメラIDと`twrmc/pose-frame-2d`）を時刻順に                                          |

再生では、録画の間隔を保ったまま、再生を始めた時刻に載せ替えます。受け取る側はフレームの古さをページの時計で
見るので、昨日の時刻のままでは全部「古い」と判断されるためです。

## local-app

[local-app](local-app.md)を参照してください。録画には校正（`configuration`）が入るので、再生ではカメラを
一切開かずに、2D→3Dまで通せます。

## camera app

| メニュー                     | 動作                                                                     |
| ---------------------------- | ------------------------------------------------------------------------ |
| ポーズの録画を始める         | 統合アプリへ送っているフレームと、空間と時刻の測定結果を記録する         |
| ポーズの録画を止めて保存する | 番号を付けて`camera-app-<番号>.json`として保存する                       |
| 録画を読み込む               | 会場のPCにある録画を一覧から選ぶ。ローカルホストが無ければファイルを選ぶ |
| 録画で再生する（カメラ不要） | カメラを開かずに、録画のフレームを時刻どおりに統合アプリへ送る           |
| 再生を止める                 | 再生を止める                                                             |

**ペアリングは本物です。** 統合アプリから見ると、WebRTCの向こうにいるのはいつものcamera appです。無いのは
カメラだけです。

**空間と時刻の校正**：再生中、または録画を読み込んでいてカメラを開いていないときは、統合アプリの校正要求に
対して、録画に入っている測定結果をそのまま返します。これで、投影パターンもカメラも無しに、統合アプリ側の
配置solveとREADY判定まで通せます。録画に測定結果が無ければ、その旨を返します。

## fusion app

| メニュー                           | 動作                                                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------------- |
| 録画を読み込む                     | 会場のPCにある録画を一覧から選ぶ。ローカルホストが無ければファイルを選ぶ                           |
| 録画で校正して再生する（接続不要） | 録画から空間と時刻の校正をやり直し、その設定で3Dサービスへ流し込む。カメラアプリとの接続は要らない |
| 再生を止める                       | 再生を止める                                                                                       |

**校正はやり直します。** 録画が持つものによって、次のどちらかになります。

- **camera appの録画**：カメラごとの測定結果（`spaceTime`）が入っているので、それをカメラアプリからの返信の
  代わりにして、四隅の実寸を入力し、配置をsolveしてREADYを判定します。当日と同じ手順です。
- **local-appの録画**：解き終わった設定（`configuration`）が入っているので、それをそのまま3Dサービスへ
  適用します。

そのあとは、録画のフレームを時刻どおりに3Dサービスへ渡し、1秒ごとに位置と3Dの状態を表示します。

## 検証の状況

- 自動：`pnpm check`。ローカルホストの`/recordings`が7件、app shellの録画・保存・読み込み・再生が13件。
- ブラウザ（camera app）：ローカルホストで配信し、フラグを手元だけで有効にして確認した。WebRTCの送信と接続
  状態、ペアリングのpeer名は差し替えた。
  - 会場のPCに置いた録画（60フレーム / 5.1秒）を一覧から読み込める。
  - 再生すると、`pose`チャンネルで相手のpeerへフレームを送る。撮影時刻は再生時刻に載せ替えられている。
  - 再生の前でも、録画を読み込んでいてカメラを開いていなければ、校正要求に録画の測定結果（`measured`、
    カメラモデル`cal-a`）で答える。
  - フラグを無効にしたビルドでは、録画のメニューもブロックも存在せず、校正要求はこれまでどおり実測の経路を
    通り、コンソールにエラーも出ない。
  - ブラウザペインが非表示だとVMのフレームが間引かれるため、送信できたのは5〜6件だった。再生は間に合わな
    かったフレームを飛ばして最新を送る（受け取る側もlatest-dataで最新だけを見る）。実機での確認が要る。
- ブラウザ（fusion app）：ローカルホストで配信し、フラグ（`debugPoseReplayV1`と`external3dServiceV1`）を
  手元だけで有効にして確認した。カメラアプリとの接続はしていない。
  - 2台分の測定結果（合成の観測）と、2台分の2Dポーズ（120フレーム / 5.1秒）を持つ録画を読み込んだ。
  - 「録画で校正して再生する」で、録画の測定結果からカメラアプリの返信を組み立て、四隅の実寸を入力して
    配置をsolveし、READYになった。
  - そのまま3Dサービスを`fusion-v0`で設定し、再生中は`ready`・人数2で、関節は`camera-1`と`camera-2`の
    2台から復元された。フレームは録画の時刻どおりに渡している。
  - 録画が終わると再生は`ended`になり、3Dサービスを止める。
- ブラウザ（実際のWebRTC越し）：カメラアプリ2つと統合アプリを別originで配信し、QRペアリングから3D出力まで
  通した。統合アプリ側は再生のフラグを持たない（いつもの受信経路の）ビルドで、カメラアプリだけが録画を再生
  している。
  - ペアリングは本物のWebRTC。OfferとAnswerのQRは画面のものをページ内でjsQRにかけて読み取り、相手へ渡した
    （ブラウザペインでカメラが使えないため）。接続後、双方向のテストメッセージも届いた。
  - カメラを止めた状態で「空間と時刻を校正する」を実行すると、2台とも録画の測定結果を返し、四隅の実寸
    （1.6 × 0.9 m）を入れて配置をsolveし、READY（2台）になった。
  - 「3D統合を開始する」のあと、2台がそれぞれ自分の録画（240フレーム / 20.7秒）を再生し、`pose`チャンネルで
    送った。統合アプリは`fusion-v0`で人数2を復元し、関節はcamera-1とcamera-2の両方から三角測量されていた。
    3D経過は70 ms前後、古いフレーム・不正・拒否はいずれも0。再生は最後（20.7秒）まで流れ、2台とも送信23件。
  - このとき見つけた不具合を直した：統合アプリは、OfferのQRを出したまま接続が成立した場合に、接続できたのに
    「接続できませんでした」と出していた（「Answerを読み取る」を押した経路しか成功として扱っていなかった）。
    接続の成立を先に見るようにした。
- ブラウザペインの制約：背面のタブはVMのフレームが落ちるため、送れたのは1秒あたり1〜2件だった（録画は12fps）。
  投影のパターンはページが隠れると自分で消えるので、確認中だけ`visibilitychange`を無効にしている。
  フレームレートと遅延の実測は実機で行う。
- 未確認：長時間の録画、実機での毎秒フレーム数と遅延。
