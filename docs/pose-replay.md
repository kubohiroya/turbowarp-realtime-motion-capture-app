# ポーズの録画と再生（DEBUG_POSE_REPLAY）

カメラの先にある処理（対応付け、三角測量、同定、アバター）は、同じ動きに対して何度も試す必要があります。
しかし本番の動きは二度と同じになりません。そこで、推定した2Dポーズを、そのときの校正ごとファイルに記録し、
あとからカメラなしで再生できるようにしています。

録るのはカメラの映像ではなく、推定したあとの2Dポーズ（COCO-17）です。

フラグ`debugPoseReplayV1`（各アプリの`packages/app-shell/src/apps/*.ts`の`appFlags`）が有効なビルドでだけ、
メニューに出ます。既定では無効で、そのときはブロックも登録されません。

## 置き場所はファイル

ブラウザの保存領域はoriginごと（アプリごとにポートが違う）なので、camera appで録ったものをfusion appから
読めません。会場用ローカルホストが`/recordings`で同じディレクトリを読み書きするので、3つのアプリが同じ録画を
使えます。置き場所は`TWRMC_RECORDINGS`、既定はホームの`multiview-pose-recordings`です。詳しくは
[ローカルホスト](local-host.md)。

ローカルホストを使わない起動（TurboWarpでSB3を開くなど）では、ファイルの書き出しと読み込みで代用します。
そのときだけは録画をページが持つので、長さは15万フレームまでです（超えると古いものから捨て、要約にそう出ます）。

## 録画の指定（長さとfps）

録画を始めるとき、長さ（秒）と、1秒あたりに記録するフレーム数（fps）を指定できます。どちらも0にすると、
その制限はかけません（0秒＝止めるまで、0fps＝推定できたフレームをすべて）。

| 指定       | 動作                                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------- |
| 長さ（秒） | その長さぶんの動きを記録したら、自動で止めます。始めてから放っておけます                                            |
| fps        | カメラごとに1秒あたりその数まで記録し、間は捨てます。長い録画を小さくしたいときや、遅いPCで再生したいときに使います |

どちらもフレーム自身の撮影時刻で判断します。ページが一瞬固まっても、録画の長さは映っている動きの長さのままです。
再生は録ったときの間隔で流すので、10fpsで録れば10fpsで再生されます。

要約の表示には、指定した値と、間引いた件数も出ます。

## 長時間の録画（実測）

`scripts/measure-recording.ts`で、記録経路そのものを測りました。カメラアプリが送るのと同じ形のフレーム
（COCO-17、座標は丸めない）を、実物のローカルホストへ同じ手順（32行ずつの書き足し）で流し、書き足しの時間、
ディスクの増え方、終わらせる時間と読み戻しの時間を測っています。カメラもMoveNetも動かしていないので、推論の
負荷と実機の揺らぎはこの数字に入っていません。

```bash
pnpm run measure:recording -- --cameras 4 --fps 12 --persons 2 --minutes 30
```

録画はローカルホストが圧縮ストリームへ書き、上限はディスク上の大きさで512 MBです。

| 構成             | 1フレーム（生） | 圧縮  | 512 MBに当たるまで | 測った長さ | ディスク | 書き足し（中央値 / p95） |
| ---------------- | --------------- | ----- | ------------------ | ---------- | -------- | ------------------------ |
| 4台 × 12fps・2人 | 3,540 B         | 3.2倍 | **168分**          | 30分       | 91.6 MB  | 3.9 ms / 4.5 ms          |
| 4台 × 12fps・6人 | 10,032 B        | 3.0倍 | **56分**           | 10分       | 90.6 MB  | 10.7 ms / 11.5 ms        |

- 書き足しは32フレームごとに1回で、4台12fpsならその間隔は0.67秒。1回が4〜11 msなので、**書き込みは律速では
  ありません**（30分ぶんを書き切るのに壁時計で11秒）
- 1回ごとにフラッシュしても、圧縮率は最後にまとめて圧縮したとき（3.2倍）と変わりませんでした
- 終わらせるのは2 ms（ストリームを閉じて名前を付け替えるだけ）
- 30分の録画（ディスク92 MB、行にして292 MB）の読み戻しは、取得0.86秒＋パース1.15秒
- 上限に当たるまで録った録画（168分、ディスク512 MB、行にして1.6 GB、483,200フレーム）も最後まで読み戻せます。
  取得と展開2.5秒＋パース5.5秒で、ヒープの増えは最大4 MB。読み戻しはページと同じく1行ずつ流し読みし、行を
  持ちません（丸ごと1つの文字列にすると、V8が持てる文字列の長さ（約512M文字）を超えて失敗していました）。
  そのため`readMs`は取得・展開・行への分割、`parseMs`は1行ずつのパースにかかった時間、`parsedHeapMB`は
  読んでいる間のヒープの増えの最大値です（以前はパースした録画全体を持ったときの増えでした）

1フレームが3.5 KBあるのは、2D座標を丸めずに送っているからです（MoveNetの値そのまま）。座標を小数2桁に
丸めると1フレーム2,247 B・圧縮6.2倍になりますが、記録の中身を変えるので入れていません。

### 長い録画の再生

再生は録画を**窓単位で**読みます。読み込みのときに1度だけ最後まで流し読みして、設定・測定結果・カメラ・
長さを覚えますが、フレームは持ちません。再生を始めると先頭から読み直し、再生位置の3秒先までを読んだところで
止まり、足りなくなったらまた読み進めます。手元にあるのは、これから配る数秒ぶんのフレームだけです
（4台12fpsで150フレームほど、0.5 MB）。

30分の録画（4台・2人、86,400フレーム、ディスク92 MB）を、ローカルホストで配信したカメラアプリに読ませました。

|                | 以前（丸ごと持つ）   | 窓単位                                |
| -------------- | -------------------- | ------------------------------------- |
| 読み込み       | 1.8秒、ヒープ+540 MB | 1.4秒、ヒープは増えない               |
| 再生中のヒープ | 627 MB               | 120〜133 MBで平ら（40秒見た）         |
| 配ったフレーム | 毎秒48件             | 毎秒48件（4台×12fpsを取りこぼさない） |
| 1回の取り出し  | 最大0.2 ms           | 最大0.3 ms                            |

これで、再生できる長さは録れる長さ（512 MB、4台12fps・2人で168分）と同じになりました。
読み込みの流し読みは録画の長さに比例するので、168分の録画なら十数秒かかる見込みです。

- 読むのが追いつかなかったとき（ページが止まった、ディスクが遅れた）は、そのカメラはしばらく新しいフレームを
  出さないだけで、再生は止まりません。実物のカメラと同じ振る舞いです
- 途中で切れた録画は、切れたところまでを録画として読み、再生します
- 再生は必ず先頭からです（途中から始める操作はありません）
- v1の録画（単一のJSON文書）は1行ずつ読めないので、これまでどおり丸ごと持ちます。v1は64 MBの上限の時代の
  もので、大きくありません

## 形式

`twrmc/pose-3d-session` v2です。1行に1つのJSONオブジェクトを並べたJSONLで、3Dサービスの評価ツール
（#34 段階2）がそのまま再生できるので、会場で録ったものを机上で指標にかけられます。

| 行          | 内容                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------ |
| `header`    | 先頭の1行。`schema`・`version`・`producer`と、3Dサービスの設定（カメラのモデル・配置・時刻対応） |
| `spaceTime` | カメラごとの空間と時刻の測定結果（`twrmc-sync-result`の中身）。camera appの録画はこれを持ちます  |
| `frame2d`   | カメラIDと`twrmc/pose-frame-2d`。録った順に並びます                                              |

### なぜ行なのか

録りながら書けるからです。1つのJSON文書だと、閉じ括弧を書くまでファイルにできないので、録画の間ずっと
全部をページのメモリに抱え、途中で落ちれば何も残りません。行なら、録れたそばから会場のPCへ書き足せます。

- ページが持つのは書き足す前の数行だけなので、長さの上限がメモリではなくディスクになります
- 途中で止まっても、そこまでが録画として読めます（最後の欠けた行は捨てて読みます）
- 読む側も最後まで読まずに処理を始められます

### 圧縮

録画はローカルホストが開いておくgzipのストリームへ書き足され、1回ごとにフラッシュされます。ディスクには
最初から圧縮した大きさしか置かれず、保存は名前の付け替えだけで済みます。置かれるのは`<名前>.jsonl.gz`で、
実測で3分の1ほどです。

読み出しはローカルホストが保存したままのバイト列をディスクから流し、ページが自分で展開します
（`DecompressionStream`）。録っている最中の録画も、途中で落ちて終端の無い録画も、フラッシュ済みのところまで
読めます。ファイルとして開くときも同じで、先頭2バイトを見て必要なら展開します。

ローカルホストが無い起動では、書き足す先が無いのでページが持ち、保存は素の`.jsonl`を書き出します。

### 以前の録画

v1（単一のJSON文書）の録画もそのまま読めます。書き出すのはv2だけです。

再生では、録画の間隔を保ったまま、再生を始めた時刻に載せ替えます。受け取る側はフレームの古さをページの時計で
見るので、昨日の時刻のままでは全部「古い」と判断されるためです。

## local-app

[local-app](local-app.md)を参照してください。録画には校正（`configuration`）が入るので、再生ではカメラを
一切開かずに、2D→3Dまで通せます。

## camera app

| メニュー                     | 動作                                                                     |
| ---------------------------- | ------------------------------------------------------------------------ |
| ポーズの録画を始める         | 統合アプリへ送っているフレームと、空間と時刻の測定結果を記録する         |
| ポーズの録画を止めて保存する | 番号を付けて`camera-app-<番号>.jsonl.gz`として保存する                   |
| 録画を読み込む               | 会場のPCにある録画を一覧から選ぶ。ローカルホストが無ければファイルを選ぶ |
| 録画で再生する（カメラ不要） | カメラを開かずに、録画のフレームを時刻どおりに統合アプリへ送る           |
| 再生を止める                 | 再生を止める                                                             |

**ペアリングは本物です。** 統合アプリから見ると、WebRTCの向こうにいるのはいつものcamera appです。無いのは
カメラだけです。

**空間と時刻の校正**：再生中、または録画を読み込んでいてカメラを開いていないときは、統合アプリの校正要求に
対して、録画に入っている測定結果をそのまま返します。これで、投影パターンもカメラも無しに、統合アプリ側の
配置solveとREADY判定まで通せます。録画に測定結果が無ければ、その旨を返します。

## fusion app

| メニュー                           | 動作                                                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------------- |
| 録画を読み込む                     | 会場のPCにある録画を一覧から選ぶ。ローカルホストが無ければファイルを選ぶ                           |
| 録画で校正して再生する（接続不要） | 録画から空間と時刻の校正をやり直し、その設定で3Dサービスへ流し込む。カメラアプリとの接続は要らない |
| 再生を止める                       | 再生を止める                                                                                       |

**校正はやり直します。** 録画が持つものによって、次のどちらかになります。

- **camera appの録画**：カメラごとの測定結果（`spaceTime`）が入っているので、それをカメラアプリからの返信の
  代わりにして、四隅の実寸を入力し、配置をsolveしてREADYを判定します。当日と同じ手順です。
- **local-appの録画**：解き終わった設定（`configuration`）が入っているので、それをそのまま3Dサービスへ
  適用します。

そのあとは、録画のフレームを時刻どおりに3Dサービスへ渡し、1秒ごとに位置と3Dの状態を表示します。

## 検証の状況

- 自動：`pnpm check`。ローカルホストの`/recordings`が14件（圧縮ストリームへの記録、録画中と途中で切れた
  録画の読み出し、停止時に閉じること、ディスク上の上限、壊れた行の拒否を含む）、app shellの録画・保存・読み込み・再生が27件（窓単位の再生、読み直し、途中で切れた録画を含む）、セッション形式（v2の行、v1の読み込み、途中で切れた
  録画）が3件。
- ブラウザ（v2の録画）：ローカルホストで配信したcamera appに、合成したフレームを40件記録させた。
  - 録画中のディスクを見ると、ヘッダ1行と32フレームが既に書かれていた（残りは書き足す前の手元の分）。
  - 保存すると`v2-take-1.jsonl.gz`になり、書きかけのファイルは消えた。中身はヘッダ1行・フレーム40行・
    測定結果1行で、この合成データでは14分の1の大きさだった。
  - 一覧から読み込んで再生すると、1.3秒ぶんが録ったときの間隔で出てきて、測定結果も返った。
  - 同じ一覧にあるv1の録画（単一のJSON文書、60フレーム）もそのまま読み込めた。
- ブラウザ（camera app）：ローカルホストで配信し、フラグを手元だけで有効にして確認した。WebRTCの送信と接続
  状態、ペアリングのpeer名は差し替えた。
  - 会場のPCに置いた録画（60フレーム / 5.1秒）を一覧から読み込める。
  - 再生すると、`pose`チャンネルで相手のpeerへフレームを送る。撮影時刻は再生時刻に載せ替えられている。
  - 再生の前でも、録画を読み込んでいてカメラを開いていなければ、校正要求に録画の測定結果（`measured`、
    カメラモデル`cal-a`）で答える。
  - フラグを無効にしたビルドでは、録画のメニューもブロックも存在せず、校正要求はこれまでどおり実測の経路を
    通り、コンソールにエラーも出ない。
  - ブラウザペインが非表示だとVMのフレームが間引かれるため、送信できたのは5〜6件だった。再生は間に合わな
    かったフレームを飛ばして最新を送る（受け取る側もlatest-dataで最新だけを見る）。実機での確認が要る。
- ブラウザ（fusion app）：ローカルホストで配信し、フラグ（`debugPoseReplayV1`と`external3dServiceV1`）を
  手元だけで有効にして確認した。カメラアプリとの接続はしていない。
  - 2台分の測定結果（合成の観測）と、2台分の2Dポーズ（120フレーム / 5.1秒）を持つ録画を読み込んだ。
  - 「録画で校正して再生する」で、録画の測定結果からカメラアプリの返信を組み立て、四隅の実寸を入力して
    配置をsolveし、READYになった。
  - そのまま3Dサービスを`fusion-v0`で設定し、再生中は`ready`・人数2で、関節は`camera-1`と`camera-2`の
    2台から復元された。フレームは録画の時刻どおりに渡している。
  - 録画が終わると再生は`ended`になり、3Dサービスを止める。
- ブラウザ（実際のWebRTC越し）：カメラアプリ2つと統合アプリを別originで配信し、QRペアリングから3D出力まで
  通した。統合アプリ側は再生のフラグを持たない（いつもの受信経路の）ビルドで、カメラアプリだけが録画を再生
  している。
  - ペアリングは本物のWebRTC。OfferとAnswerのQRは画面のものをページ内でjsQRにかけて読み取り、相手へ渡した
    （ブラウザペインでカメラが使えないため）。接続後、双方向のテストメッセージも届いた。
  - カメラを止めた状態で「空間と時刻を校正する」を実行すると、2台とも録画の測定結果を返し、四隅の実寸
    （1.6 × 0.9 m）を入れて配置をsolveし、READY（2台）になった。
  - 「3D統合を開始する」のあと、2台がそれぞれ自分の録画（240フレーム / 20.7秒）を再生し、`pose`チャンネルで
    送った。統合アプリは`fusion-v0`で人数2を復元し、関節はcamera-1とcamera-2の両方から三角測量されていた。
    3D経過は70 ms前後、古いフレーム・不正・拒否はいずれも0。再生は最後（20.7秒）まで流れ、2台とも送信23件。
  - このとき見つけた不具合を直した：統合アプリは、OfferのQRを出したまま接続が成立した場合に、接続できたのに
    「接続できませんでした」と出していた（「Answerを読み取る」を押した経路しか成功として扱っていなかった）。
    接続の成立を先に見るようにした。
- ブラウザペインの制約：背面のタブはVMのフレームが落ちるため、送れたのは1秒あたり1〜2件だった（録画は12fps）。
  投影のパターンはページが隠れると自分で消えるので、確認中だけ`visibilitychange`を無効にしている。
  フレームレートと遅延の実測は実機で行う。
- 長時間の録画：上の「長時間の録画（実測）」。圧縮ストリームへの記録と、30分の録画の窓単位の再生を測った。
- 未確認：実機での毎秒フレーム数と遅延（MoveNetを動かしながらの書き足し、実カメラの揺らぎ）。
