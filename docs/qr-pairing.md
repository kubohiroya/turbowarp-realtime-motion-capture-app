# QRペアリング（M-07）

camera appとfusion appを、QRコードの往復でWebRTC接続します。搬送形式、part、hash、peerの対応、期限は
[`turbowarp-webrtc-qrcode-pairing`](https://github.com/kubohiroya/turbowarp-webrtc-qrcode-pairing)が
担当し、このリポジトリのscriptは、partを画面に出すこと、運用者のボタン操作を手順に変えること、
結果を表示することだけを担当します（`scripts/app-scripts/pairing.ts`）。

## 操作

| 端末       | 操作                                                 | 画面                                                                |
| ---------- | ---------------------------------------------------- | ------------------------------------------------------------------- |
| fusion app | メニュー「カメラアプリと接続する」                   | OfferのQRを全画面表示（`Offer（camera-N） i / n`）                  |
| camera app | カメラを選んでから、メニュー「統合アプリと接続する」 | 投影されたOfferをこのカメラで読み取り、AnswerのQRを全画面表示       |
| 担当者     | AnswerのQRをスマートフォンで撮影し、統合PCへ運ぶ     | —                                                                   |
| fusion app | 「Answerを読み取る」                                 | 統合PCのカメラのpreviewを出し、スマートフォンのQRを読み取る         |
| 両方       | 自動                                                 | 接続後、互いに`twrmc-link-test`を送り、受信したメッセージを表示する |

- QRが複数枚のときは「次のQR」で1枚ずつ進めます。撮影する人のために、自動では巡回しません。
- 「やめる」またはメニュー「接続をやめる」でその交換だけを取り消します。成立済みの接続は切りません。
- fusion appは接続のたびに`camera-1`、`camera-2`…と別のsessionを開くため、別のcamera appの
  Answerが前の交換を完了させることはありません。
- 接続は成立したのに10秒以内に相手のテストメッセージが届かない場合は、エラーとして表示します。

## 構成

- 両SB3はステージだけのprojectなので、partはスプライトではなく、app shellのQRパネル
  （`show QR image [IMAGE] caption [CAPTION] buttons [BUTTONS]`）に、ペアリング拡張が作るdata URIで
  表示します。白地・正方形・非平滑化で、quiet zoneを削りません。
- QRの読取りはペアリング拡張が`turbowarp-jsqr`のruntime capabilityで行い、sessionの間1つのcamera leaseを
  保持します。アプリはjsQRの結果をruntime variableで受け取らないため、Temporary Variables拡張への
  依存（#19）はこの経路にはありません。
- WebRTCはcapability v3が必要なため、`turbowarp-webrtc`を0.4.0へ上げています。

## feature flagと切戻し

`qrCourierPairing`（起動時固定）が両アプリで有効のときだけメニューに現れます。app shellはこの値を
ペアリング拡張の`__TWQP_FEATURE_FLAGS__.qrCodePairing`へも書きます。切り戻すときは
`packages/app-shell/src/apps/*.ts`の`featureFlags`から外してビルドし直します。ペアリング拡張の
ブロックが消え、manual pairing（`turbowarp-webrtc`の`create offer code`など）が残ります。

## 実カメラでの確認

ペアリングで光学的にやり取りするのは2回です。統合アプリが投影したOfferを**カメラアプリのカメラ**が読み、
カメラアプリの画面のAnswerを**スマートフォンで撮って**統合PCの**カメラ**に見せます。どちらも、きれいに
スキャンした画像ではなく、小さく、ぼけ、投影で薄まり、斜めから見た画像です。ここでは、それを会場の機材で
確かめる手順と、机上で見積もった「どのくらいの大きさで写れば読めるか」の目安をまとめます。

### 準備

- 統合PC（fusion app）、プロジェクタ、カメラアプリのPCとカメラ、スマートフォン、統合PCのカメラ（Answerを
  読むもの。ノートPCの内蔵カメラでよい）
- 両アプリを`pnpm run serve:app -- fusion-app`／`serve:app -- camera-app`で、いつものポートで起動する
- 会場の照明を本番と同じにする（投影のコントラストが一番効く）

### 手順

1. **Offerの読取り（投影 → カメラ）**
   1. 統合アプリで「カメラアプリと接続する」。OfferのQRが全画面で投影される。キャプションの`i / n`で
      part数を控える。
   2. カメラアプリで「カメラを選ぶ」→「統合アプリと接続する」。カメラを投影に向ける。
   3. 読めるまでの時間を測る（プレビューにQRが入ってから、Answerが表示されるまで）。30秒で読めなければ
      「読めない」とする。
   4. 読めたときの、カメラの画像の中でのQRの大きさ（プレビューで何割を占めたか）と、カメラから投影面までの
      距離、投影の横幅を控える。
2. **Answerの読取り（スマートフォン → 統合PCのカメラ）**
   1. カメラアプリに出たAnswerのQRをスマートフォンで撮る。
   2. 統合アプリで「Answerを読み取る」。スマートフォンの画面を統合PCのカメラに向ける。
   3. 読めるまでの時間、スマートフォンとカメラの距離、画面の明るさを控える。
3. **接続とテストメッセージ**：両方に「接続しました（相手: …）。テストメッセージを送受信できました」が出る
   ことを確かめる。出なければ、画面のエラーコードを控える。
4. **別PC間のICE**：カメラアプリと統合アプリを別のPC（同じLAN）で動かし、手順1〜3を通す。つながらなければ、
   両PCのネットワーク（有線／無線、同じサブネットか）と、ファイアウォールの設定を控える。
5. **条件を変える**：下の表の条件を1つずつ変えて、手順1を繰り返す。

| 変える条件     | 例                                   |
| -------------- | ------------------------------------ |
| 距離           | カメラから投影面まで 1 m / 2 m / 4 m |
| 投影の大きさ   | 投影の横幅 1 m / 2 m                 |
| 照明           | 暗転 / 客電あり / 作業灯             |
| 角度           | 正面 / 横から30° / 45°               |
| カメラの解像度 | 1280x720 / 1920x1080                 |
| スマートフォン | 画面の明るさ 最大 / 自動             |

### 机上の目安（`pnpm run measure:qr`）

実機で試す前に、どのくらいの大きさで写れば読めるかを机上で見積もりました。ペアリング拡張と同じ符号化
（`qrcode`、誤り訂正M）で作ったQRを、カメラの画像のように描き（画像の中で5°回した上で、ぼかし・投影で薄まった
コントラスト・カメラからの傾き・センサーの雑音を加える）、アプリと同じ復号器（jsQR）で読めるかを調べます。
レンズの歪み、モアレ、露出の飛び、圧縮は入っていないので、実機はこれより厳しいと見てください。

ペアリング拡張は、1つのpartにQRのversion 40までぎっしり詰めます。Offerは約1,450文字なので**1枚のversion 32
（145モジュール）**になり、カメラで読むにはかなり細かいQRです。

| part数（Offer） | QR（静域込み）            | 読めた条件 720p | 読めた条件 1080p | 正面・くっきりで要る大きさ 720p | 同 1080p               |
| --------------- | ------------------------- | --------------- | ---------------- | ------------------------------- | ---------------------- |
| 1（今の既定）   | version 32、153モジュール | 6 / 27          | 8 / 27           | 612 px（画像の高さの85%）       | 612 px（57%）          |
| 2               | version 24、121モジュール | 5 / 27          | 8 / 27           | 605 px（84%）                   | 読めず（下の注を参照） |
| 3               | version 22、113モジュール | 8 / 27          | —                | 452 px（63%）                   | —                      |
| 4               | version 20、105モジュール | 12 / 27         | 17 / 27          | 525 px（73%）                   | 525 px（49%）          |

条件は、コントラスト（1 / 0.5 / 0.25）× ぼかし（0 / 1 / 2 px）× カメラの傾き（0° / 30° / 45°）の27通りです。

分かったこと：

- **傾きがいちばん効きます。** 1枚のOfferは、30°傾けると720pでは一度も読めず、1080pでも9条件のうち1つ
  （コントラスト0.25・ぼかし1 px）だけでした。4枚に分けると、30°で読める条件は720pで4、1080pで7に増えます。
  45°は、4枚のときに720pと1080pで1条件ずつ読めただけでした。カメラはできるだけ投影の正面に置きます。
- **1枚のOfferは、正面でもカメラの画像の高さの85%（720p）／57%（1080p）を占める必要があります。** 投影の
  QRがカメラの画面いっぱいに写るくらいまで近づけるか、大きく投影します。
- **ぼかし2 pxで1枚のOfferは読めなくなります。** ピントを合わせます。
- **センサーの雑音が明るさの2%を超えると、大きさに関係なく読めなくなります。** jsQRの二値化が、平らな白の
  上の雑音を模様と取り違えるためです（1.5%までは読めました）。暗い会場でカメラのゲインが上がると起こり得ます。
- 分けるほど（versionが小さいほど）読める条件は増えますが、運ぶ枚数が増えます。今の拡張はpartの大きさを
  変える設定を持たない（誤り訂正の強さだけ）ので、分け方を変えるならペアリング拡張側の変更になります。

どの条件でも「大きい方から試して、初めて読めなかったところで止める」ので、jsQRがたまたま1つの大きさで
読み損ねると、その条件は読めない側に数えられます（2枚・1080p・正面で「読めず」になったのはこのためで、
小さい大きさなら読めています）。個々の数字より傾向として見てください。

## 検証の状況

- 自動：`pnpm check`（app shellのQRパネル・フラグのテストを含む）。
- ブラウザ：ローカルホストで両アプリを別originに配信し、fusion appのOffer作成からcamera appのAnswer表示、
  fusion appでの接続成立、双方向のテストメッセージ、取消までをメニュー操作で通した。ただし
  ブラウザペインではカメラを使えないため、QRの読取りは表示中の画像をページ内でjsQRにかけ、
  読み取った文字列を`receive pairing QR text`へ渡して代替した。
- ブラウザ（2台のカメラアプリ）：[ポーズの録画と再生](pose-replay.md)の確認の中で、camera-1とcamera-2を
  続けてペアリングし、両方とも接続とテストメッセージまで通した。このとき、Offerを出したまま接続が成立すると
  統合アプリが「接続できませんでした」と出す不具合を見つけて直した（`scripts/app-scripts/fusion-app.ts`：
  ボタンの結果より先に接続の成立を見る）。
- ブラウザ（カメラの読取りの経路を通して）：カメラの代わりにQRを描いた画面を`getUserMedia`として渡し、
  アプリ自身の読取り（`scan pairing QR from camera`、Camera Sourceのフレーム→jsQR）でペアリングを通した。
  - カメラアプリが、投影に見立てたOffer（1枚、version 31、1モジュール4.5 px、5°回転）を自分のカメラで読み、
    Answerを表示した。
  - 統合アプリで「Answerを読み取る」を押し、Answer（1枚、version 32、1モジュール4.4 px、5°回転）を統合PCの
    カメラ（`pairing`）で読んで、7.3秒で接続し、双方向のテストメッセージが届いた。
  - それまでの確認では読取りを文字列の受け渡しで代えていたが、これで両方向とも読取りの経路そのものを通した。
- 未確認：実カメラでの読取り（上の「実カメラでの確認」の手順）、プロジェクタ投影とスマートフォン撮影、
  別PC間のICE、複数part。
