# QRペアリング（M-07）

camera appとfusion appを、QRコードの往復でWebRTC接続します。搬送形式、連結QRコード、hash、peerの対応、
期限は[`turbowarp-webrtc-qrcode-pairing`](https://github.com/kubohiroya/turbowarp-webrtc-qrcode-pairing)
0.2.2が担当し、このリポジトリのscriptは、QRを画面に出すこと、運用者のボタン操作を手順に変えること、
読み取りの結果を表示することだけを担当します（`scripts/app-scripts/pairing.ts`）。

OfferとAnswerは、それぞれ1つの連結QRコード（Structured Append、ISO/IEC 18004）として運びます。各QRは規格の
headerに自分の位置と枚数を持つので、読む側は順番を問わずに集められます。

## 操作

| 端末       | 操作                                                 | 画面                                                                              |
| ---------- | ---------------------------------------------------- | --------------------------------------------------------------------------------- |
| fusion app | メニュー「カメラアプリと接続する」                   | OfferのQRを全画面で、約0.8秒ずつコマ送りでループ表示（`Offer（camera-N） i / n`） |
| camera app | カメラを選んでから、メニュー「統合アプリと接続する」 | 投影されたOfferを順不同で読み、全部そろったらAnswerのQRを全画面表示               |
| 担当者     | AnswerのQRをスマートフォンで撮影し、統合PCへ運ぶ     | —                                                                                 |
| fusion app | 「Answerを読み取る」                                 | 統合PCのカメラのpreviewを出し、スマートフォンのQRを読み取る                       |
| 両方       | 自動                                                 | 接続後、互いに`twrmc-link-test`を送り、受信したメッセージを表示する               |

- OfferのQRは統合アプリが自動で切り替えます。カメラアプリのカメラは投影に向けたままにし、順番も枚数も
  気にする必要はありません。読み逃したQRは次の周回でまた来ます。
- 読み取りの結果は、状態の1行に出ます。新しいQRを受け取ると、すぐにその行に替わります。カメラは目の前の
  QRを1秒に何度も読むので、読み取り済みのQRや別のペアリングのQRは、今の行が1.5秒出たあとでなければ
  書き換えません。
  - 「QRコードを読み取りました（2 / 4）。あと 2 枚です。」— 新しいQRを受け取った
  - 「このQRコードは読み取り済みです（2 / 4）。あと 2 枚です。」— 同じQRをもう一度読んだ。害はない
  - 「注意: 別のペアリングのQRコードを読んだため、無視しました（message-mismatch）。」— 別の交換のQRや
    古い投影のQR。集めているものには影響しない。括弧内は理由のコード
  - 「QRコードを全部読み取りました（4 枚）。」— 全部そろった。読取りのブロックが終わった直後に出す
- AnswerのQRはスマートフォンで1枚ずつ撮るため、カメラアプリでは「次のQR」で手で進めます。統合アプリで
  読むときも、順番は問いません。
- 「やめる」またはメニュー「接続をやめる」でその交換だけを取り消します。成立済みの接続は切りません。
- fusion appは接続のたびに`camera-1`、`camera-2`…と別のsessionを開くため、別のcamera appの
  Answerが前の交換を完了させることはありません。
- 接続は成立したのに10秒以内に相手のテストメッセージが届かない場合は、エラーとして表示します。

## 構成

- 両SB3はステージだけのprojectなので、QRはスプライトではなく、app shellのQRパネル
  （`show QR image [IMAGE] caption [CAPTION] buttons [BUTTONS]`）に、ペアリング拡張が作るdata URIで
  表示します。白地・正方形・非平滑化で、quiet zoneを削りません。
- QRの読取りはペアリング拡張が`turbowarp-jsqr` 0.4.0（zxing-cpp）の`readFrame`で行い、連結QRコードの
  位置も受け取ります。sessionの間1つのcamera leaseを保持します。読取りのブロックは連結QRがそろうまで
  scriptを止めるため、読み取りのたびの状態の表示は、`pairing QR read report`を受け取った別のscriptが
  `pairing QR reads`の増加を見て行います（`PairingSteps.scanWithReport`／`readReportScript`）。
- 1枚のQRのversionの上限は、ペアリング拡張の既定のまま（Offer 15、Answer 20）です。アプリはjsQRの結果をruntime variableで受け取らないため、Temporary Variables拡張への
  依存（#19）はこの経路にはありません。
- WebRTCはcapability v3が必要なため、`turbowarp-webrtc`を0.4.0へ上げています。

## feature flagと切戻し

`qrCourierPairing`（起動時固定）が両アプリで有効のときだけメニューに現れます。app shellはこの値を
ペアリング拡張の`__TWQP_FEATURE_FLAGS__.qrCodePairing`へも書きます。切り戻すときは
`packages/app-shell/src/apps/*.ts`の`featureFlags`から外してビルドし直します。ペアリング拡張の
ブロックが消え、manual pairing（`turbowarp-webrtc`の`create offer code`など）が残ります。

## 実カメラでの確認

ペアリングで光学的にやり取りするのは2回です。統合アプリが投影したOfferを**カメラアプリのカメラ**が読み、
カメラアプリの画面のAnswerを**スマートフォンで撮って**統合PCの**カメラ**に見せます。どちらも、きれいに
スキャンした画像ではなく、小さく、ぼけ、投影で薄まり、斜めから見た画像です。ここでは、それを会場の機材で
確かめる手順と、机上で見積もった「どのくらいの大きさで写れば読めるか」の目安をまとめます。

### 準備

- 統合PC（fusion app）、プロジェクタ、カメラアプリのPCとカメラ、スマートフォン、統合PCのカメラ（Answerを
  読むもの。ノートPCの内蔵カメラでよい）
- 両アプリを`pnpm run serve:app -- fusion-app`／`serve:app -- camera-app`で、いつものポートで起動する
- 会場の照明を本番と同じにする（投影のコントラストが一番効く）

### 手順

1. **Offerの読取り（投影 → カメラ）**
   1. 統合アプリで「カメラアプリと接続する」。OfferのQRが全画面でループ投影される。キャプションの`i / n`で
      枚数を控える。
   2. カメラアプリで「カメラを選ぶ」→「統合アプリと接続する」。カメラを投影に向ける。
   3. 読めるまでの時間を測る（プレビューにQRが入ってから、Answerが表示されるまで）。30秒で読めなければ
      「読めない」とする。途中の状態の1行（あと何枚か、別のQRを読んだか）も控える。
   4. 読めたときの、カメラの画像の中でのQRの大きさ（プレビューで何割を占めたか）と、カメラから投影面までの
      距離、投影の横幅を控える。
2. **Answerの読取り（スマートフォン → 統合PCのカメラ）**
   1. カメラアプリに出たAnswerのQRを、「次のQR」で送りながら全部スマートフォンで撮る。
   2. 統合アプリで「Answerを読み取る」。スマートフォンの画面を統合PCのカメラに向ける。
   3. 読めるまでの時間、スマートフォンとカメラの距離、画面の明るさを控える。
3. **接続とテストメッセージ**：両方に「接続しました（相手: …）。テストメッセージを送受信できました」が出る
   ことを確かめる。出なければ、画面のエラーコードを控える。
4. **別PC間のICE**：カメラアプリと統合アプリを別のPC（同じLAN）で動かし、手順1〜3を通す。つながらなければ、
   両PCのネットワーク（有線／無線、同じサブネットか）と、ファイアウォールの設定を控える。
5. **条件を変える**：下の表の条件を1つずつ変えて、手順1を繰り返す。

| 変える条件     | 例                                   |
| -------------- | ------------------------------------ |
| 距離           | カメラから投影面まで 1 m / 2 m / 4 m |
| 投影の大きさ   | 投影の横幅 1 m / 2 m                 |
| 照明           | 暗転 / 客電あり / 作業灯             |
| 角度           | 正面 / 横から30° / 45°               |
| カメラの解像度 | 1280x720 / 1920x1080                 |
| スマートフォン | 画面の明るさ 最大 / 自動             |

### 机上の目安（`pnpm run measure:qr`）

実機で試す前に、どのくらいの大きさで写れば読めるかを机上で見積もりました。ペアリング拡張と同じ作り方
（`@kubohiroya/qrcode-structured-append`で作る連結QRコード、誤り訂正M、versionの上限つき）のQRを、カメラの
画像のように描き（画像の中で5°回した上で、ぼかし・投影で薄まったコントラスト・カメラからの傾き・センサーの
雑音1%を加える）、アプリと同じ復号器（`turbowarp-jsqr` 0.4.0が使うzxing-cpp）で、連結QRの位置まで正しく
読めるかを調べます。レンズの歪み、モアレ、露出の飛び、圧縮は入っていないので、実機はこれより厳しいと
見てください。

測ったのは、Offerの接続情報1,457文字にheaderを付けた1,766文字のメッセージです（ブラウザで作ったOfferは
これより少し短く、version 15で4枚でした）。条件は、コントラスト（1 / 0.5 / 0.25）× ぼかし（0 / 1 / 2 px）×
カメラの傾き（0° / 30° / 45°）の27通りで、1モジュールあたりの画素数ごとに、27条件のうちいくつ読めたかを
数えます。

| versionの上限      | 枚数 | 1枚のQR（静域込み）       | 27条件のうち読めた数（720p）<br>2 / 3 / 4 / 5 / 6 px/モジュール | 同（1080p）<br>2 / 3 / 4 / 5 / 6 px/モジュール |
| ------------------ | ---- | ------------------------- | --------------------------------------------------------------- | ---------------------------------------------- |
| 15（Offerの既定）  | 5    | version 14、81モジュール  | 6 / 16 / 18 / 24 / 24                                           | 5 / 17 / 18 / 23 / 26                          |
| 20（Answerの既定） | 3    | version 19、101モジュール | 6 / 15 / 18 / 22 / 24                                           | 6 / 17 / 18 / 23 / 25                          |
| 40（1枚にする）    | 1    | version 35、165モジュール | 5 / 14 / 6 / — / —                                              | 6 / 15 / 18 / 22 / 9                           |

「—」はその大きさではフレームに収まらないことを表します。復号の時間の中央値は、720pで5〜6 ms、1080pで
10〜13 msでした。

分かったこと：

- **読めるかどうかは、1モジュールが何画素に写るかでほぼ決まります。** 同じ画素数なら、version 15でも20でも
  読める条件の数はほとんど同じです。3.5〜4 px/モジュールで27条件のうち18、5 px/モジュールで22〜24です。
- **同じ大きさに写すなら、versionが小さいほど1モジュールが大きく写ります。** 例えば、カメラの画像の高さの
  半分（720pで360 px）に写すと、version 14は約4.4 px/モジュール（18〜24条件）、version 19は約3.6 px/
  モジュール（約18条件）、1枚のversion 35は約2.2 px/モジュール（約5条件）です。Offerを1枚にせず、version 15
  までの数枚に分けてループ表示するのはこのためです。
- **ぼかし2 pxでは、5 px/モジュール以上が必要です。** それより小さいと、どのversionでも読めません。ピントを
  合わせます。
- **45°の傾きは、3.5 px/モジュール以上でようやく読めるようになります。** カメラはできるだけ投影の正面に
  置きます。
- 大きすぎても読めないことがあります（720pで画像の高さの9割に写したversion 14や、1枚のversion 35）。
  45°に傾けた大きなQRの手前の辺が、画像からはみ出すためです。
- 以前のjsQRは、センサーの雑音が2%を超えると大きさに関係なく読めなくなりましたが、zxing-cppはそうなりません。
  version 15、720pで雑音を2% / 3% / 5%に上げても、5 px/モジュールで27条件のうち23 / 21 / 19が読めました
  （1%では24）。雑音が増えるほど、大きく写す必要があります。

1つの条件で大きさによって読めたり読めなかったりすることがあるので（復号器がたまたま1つの大きさで読み損ねる
ため）、個々の数字より傾向として見てください。

## 検証の状況

- 自動：`pnpm check`（app shellのQRパネル・フラグのテストを含む）。
- ブラウザ：ローカルホストで両アプリを別originに配信し、fusion appのOffer作成からcamera appのAnswer表示、
  fusion appでの接続成立、双方向のテストメッセージ、取消までをメニュー操作で通した。ただし
  ブラウザペインではカメラを使えないため、QRの読取りは表示中の画像をページ内でjsQRにかけ、
  読み取った文字列を`receive pairing QR text`へ渡して代替した。
- ブラウザ（2台のカメラアプリ）：[ポーズの録画と再生](pose-replay.md)の確認の中で、camera-1とcamera-2を
  続けてペアリングし、両方とも接続とテストメッセージまで通した。このとき、Offerを出したまま接続が成立すると
  統合アプリが「接続できませんでした」と出す不具合を見つけて直した（`scripts/app-scripts/fusion-app.ts`：
  ボタンの結果より先に接続の成立を見る）。
- ブラウザ（カメラの読取りの経路を通して）：カメラの代わりにQRを描いた画面を`getUserMedia`として渡し、
  アプリ自身の読取り（`scan pairing QR from camera`、Camera Sourceのフレーム→jsQR）でペアリングを通した。
  - カメラアプリが、投影に見立てたOffer（1枚、version 31、1モジュール4.5 px、5°回転）を自分のカメラで読み、
    Answerを表示した。
  - 統合アプリで「Answerを読み取る」を押し、Answer（1枚、version 32、1モジュール4.4 px、5°回転）を統合PCの
    カメラ（`pairing`）で読んで、7.3秒で接続し、双方向のテストメッセージが届いた。
  - それまでの確認では読取りを文字列の受け渡しで代えていたが、これで両方向とも読取りの経路そのものを通した。
- ブラウザ（連結QRコードとOfferのループ表示、ペアリング拡張0.2.2）：上と同じ方法で、カメラの代わりに
  統合アプリのOfferを描いた画面を渡し、カメラアプリ自身の読取りでペアリングを通した。
  - 統合アプリはOfferを4枚（version 15）に分け、0.82〜0.94秒ずつループ表示した。
  - カメラアプリは、ループの途中から「2 / 4 → 3 / 4 → 4 / 4 → 1 / 4」の順で読んだ。状態の行は新しいQRの
    たびに「読み取りました（k / 4）。あと n 枚です。」に替わり、重複読取りで上書きされなかった。約3.9秒で
    全部そろい、「QRコードを全部読み取りました（4 枚）。」を出してAnswer（3枚、version 20）を表示した。
  - 統合アプリで「Answerを読み取る」を押し、Answerを「3 / 3 → 2 / 3 → 1 / 3」の逆順で見せた。同じQRが
    写り続けたときは1.5秒後に「読み取り済みです」を出し、約4.4秒で接続して、双方向のテストメッセージが
    届いた。
  - この確認の途中で、ペアリング拡張0.2.0では同じQRが写り続けるとカメラアプリが応答しなくなることが
    分かった（読取りのループがタイマーを挟まずに回り続けていた）。0.2.1で直している。0.2.2では、レビューで
    見つかった収集の問題（headerが1枚目に収まらない設定、同時の読取り、規格に合わないQR）を直している。
- 未確認：実カメラでの読取り（上の「実カメラでの確認」の手順）、プロジェクタ投影とスマートフォン撮影、
  別PC間のICE。
